# Architecture: Database Schema & RAG Pipeline

## Database Schema

The application uses PostgreSQL with the `pgvector` extension, managed through SQLAlchemy 2.x with async support (`asyncpg` driver). The database is initialized at bot startup in `main.py`, which creates the `vector` extension and runs `Base.metadata.create_all`.

The schema is split across two model files: `core/models.py` (bot domain) and `core/wsp_models.py` (schedule domain).

### Bot Domain Models (`core/models.py`)

#### `knowledge_base` — KnowledgeItem

The core RAG data store. Each row represents a curated text chunk about the university.

| Column | Type | Description |
|---|---|---|
| `id` | `Integer` PK | Auto-incremented identifier |
| `content` | `Text` | The knowledge entry text (displayed to the user) |
| `category` | `String` | Topic category (e.g., "Retake", "AddDrop") |
| `embedding` | `Vector(768)` | 768-dimensional embedding generated by `intfloat/multilingual-e5-base` |
| `created_at` | `DateTime(tz)` | Server-side timestamp |

#### `files` — FileItem

Documents and photos indexed from a linked Telegram channel.

| Column | Type | Description |
|---|---|---|
| `id` | `Integer` PK | Auto-incremented identifier |
| `file_id` | `String` | Telegram file ID (used to re-send the file) |
| `file_unique_id` | `String` UNIQUE | Telegram's immutable file identifier (used for upsert deduplication) |
| `caption` | `Text` | File description / caption text |
| `type` | `String` | File type: `"document"` or `"photo"` |
| `category` | `String` | Hashtag-derived category: `"map"`, `"calendar"`, `"rup"`, or `NULL` |
| `embedding` | `Vector(768)` | Embedding of `"Filename: {name}. Description: {caption}"` |
| `created_at` | `DateTime(tz)` | Server-side timestamp |

#### `users` — User

Registered bot users with quota tracking.

| Column | Type | Description |
|---|---|---|
| `telegram_id` | `BigInteger` PK | Telegram user ID |
| `full_name` | `String` | User's display name |
| `username` | `String` | Telegram username |
| `joined_at` | `DateTime(tz)` | First interaction timestamp |
| `last_active` | `DateTime(tz)` | Auto-updated on each interaction (`onupdate=func.now()`) |
| `requests_left` | `Integer` | Remaining AI requests in the current quota window (default: 50) |
| `quota_reset_at` | `DateTime(tz)` | Timestamp when the quota resets (24-hour rolling window) |

#### `interaction_logs` — InteractionLog

Stores every AI Q&A interaction for RLHF analysis.

| Column | Type | Description |
|---|---|---|
| `id` | `Integer` PK | Auto-incremented identifier |
| `telegram_id` | `BigInteger` FK → `users.telegram_id` | The user who initiated the query |
| `user_query` | `Text` | The user's original question |
| `bot_response` | `Text` | The AI-generated answer |
| `feedback` | `Integer` | User feedback: `1` (like), `-1` (dislike), `0` (no feedback) |
| `created_at` | `DateTime(tz)` | Server-side timestamp |

### Schedule Domain Models (`core/wsp_models.py`)

These models store data scraped from the KBTU WSP portal.

#### `subjects` — Subject

| Column | Type | Description |
|---|---|---|
| `id` | `Integer` PK | Auto-incremented identifier |
| `code` | `String(20)` UNIQUE | Subject code (e.g., `"CSS201"`) |
| `name_ru` / `name_kz` / `name_en` | `String(255)` | Subject name in three languages |
| `department` | `String(255)` | Offering department |
| `credits` | `Float` | ECTS credit value |
| `formula` | `String(20)` | Teaching format (e.g., `"1/0/2"` = 1 Lecture / 0 Practice / 2 Labs) |
| `year` / `period` | `String` | Academic year and semester period |

**Relationship:** `Subject` → `ScheduleEvent` (one-to-many, cascade delete)

#### `instructors` — Instructor

| Column | Type | Description |
|---|---|---|
| `id` | `Integer` PK | Auto-incremented identifier |
| `full_name` | `String(255)` UNIQUE | Instructor's full name |

#### `rooms` — Room

| Column | Type | Description |
|---|---|---|
| `id` | `Integer` PK | Auto-incremented identifier |
| `number` | `String(50)` UNIQUE | Room number (e.g., `"332б"`, `"Independence Hall"`) |
| `street` | `String(255)` | Street address (nullable) |

#### `schedule_events` — ScheduleEvent

The central schedule table with a composite unique constraint.

| Column | Type | Description |
|---|---|---|
| `id` | `Integer` PK | Auto-incremented identifier |
| `subject_id` | FK → `subjects.id` | ON DELETE CASCADE |
| `instructor_id` | FK → `instructors.id` | ON DELETE RESTRICT |
| `room_id` | FK → `rooms.id` | ON DELETE RESTRICT |
| `day_of_week` | `Enum(DayOfWeek)` | Day: Mon–Sat |
| `start_time` | `Time` | Lesson start time (derived from CSS pixel offset during scraping) |
| `end_time` | `Time` | Lesson end time |
| `lesson_type` | `Enum(LessonType)` | Л (Lecture), П (Practice), Лаб (Lab) |
| `group_info` | `String(50)` | Raw capacity string, e.g., `"76/75"` |
| `student_count_current` | `Integer` | Parsed current enrollment |
| `student_count_max` | `Integer` | Parsed maximum capacity |

**Unique constraint:** `(subject_id, day_of_week, start_time, lesson_type, room_id)` — prevents duplicate event entries for the same slot.

## The RAG Pipeline

The Retrieval-Augmented Generation pipeline is implemented across three modules: `services/embeddings.py`, `services/repo.py`, and `services/ai_service.py`. It is invoked by the catch-all handler in `bot/handlers/ai.py`.

### Data Flow

```
User Message
    │
    ▼
[1] Quota Check ──── (denied) ──→ "Limit reached" response
    │
    (allowed)
    ▼
[2] Embed Query ──── get_vector(text, is_query=True) ──→ 768-dim vector
    │                 prefix: "query: " (E5 format)
    ▼
[3] Vector Search ── KnowledgeItem.embedding.cosine_distance(query_vec)
    │                 ORDER BY distance ASC, LIMIT 3
    │                 Filter: distance ≤ 0.7
    ▼
[4] File Search ──── FileItem.embedding.cosine_distance(query_vec)
    │                 ORDER BY distance ASC, LIMIT 3
    │                 Filter: distance ≤ 0.2 (stricter threshold)
    ▼
[5] LLM Generation ─ Groq API (llama-3.1-8b-instant)
    │                 System prompt: "Answer ONLY from context. If no answer → NO_INFO"
    │                 User content: "Вопрос: {question}\n\nКонтекст:\n{context}"
    ▼
[6] Response Logic
    ├── AI returns valid answer → send answer + 👍/👎 buttons
    │                              log to interaction_logs
    ├── AI returns "NO_INFO" + files found → send file notice
    └── AI returns "NO_INFO" + no files  → send "don't know" message
    │
    ▼
[7] File Delivery ── Send matched files (documents/photos) via Telegram API
```

### Embedding Model

The project uses `intfloat/multilingual-e5-base`, a 768-dimensional multilingual embedding model. This model requires explicit text prefixing per the E5 specification:

- **Passages** (stored data): prefixed with `"passage: "` before encoding.
- **Queries** (user questions): prefixed with `"query: "` before encoding.

This asymmetric prefixing is handled by the `get_vector()` function in `services/embeddings.py`. The model is loaded lazily (singleton pattern) on first use.

### Knowledge Enrichment

When inserting knowledge base entries, the embedding is computed not from the raw content alone but from an enriched string:

```
"Topic: {category}. Keywords: {keywords}. Content: {content}"
```

This enrichment improves retrieval precision by incorporating metadata into the vector representation. The original clean content (without enrichment) is stored in the `content` column and displayed to the user.

### Similarity Search

Both `search_knowledge()` and `search_files()` functions in `services/repo.py` use **Cosine Distance** provided by pgvector:

```python
distance_col = KnowledgeItem.embedding.cosine_distance(query_vector).label("distance")
stmt = select(KnowledgeItem, distance_col).order_by(distance_col).limit(limit)
```

- Cosine distance of `0.0` = identical vectors.
- The knowledge base uses a threshold of `≤ 0.7` (broader match).
- The file search uses a threshold of `≤ 0.2` (strict match, since file embeddings are based on filenames/captions, which are less semantically rich).

### LLM Integration

The AI service (`services/ai_service.py`) sends a structured prompt to the Groq API using `llama-3.1-8b-instant`:

- **System prompt** instructs the model to answer exclusively from the provided context. If the context does not contain a direct answer, the model must respond with the literal token `NO_INFO`.
- **User content** concatenates the user's question with the retrieved context.

The `NO_INFO` sentinel is then checked by the handler to switch between answer delivery and fallback logic.

## Schedule Logic

### Data Source: WSP Scraper

The `wsp_scraper/` module is a standalone Playwright-based scraper that:

1. Logs into the KBTU WSP portal (`wsp.kbtu.kz`).
2. Navigates to the Subject Schedule grid view.
3. Iterates through each subject row, double-clicking to open its schedule view.
4. Extracts schedule blocks by parsing CSS `top` pixel offsets (to derive time slots) and inner text (to extract instructor, room, lesson type, and capacity).
5. Applies validation rules (drops Sunday entries and low-capacity ghost groups).
6. Upserts the data into the normalized database schema (`subjects`, `instructors`, `rooms`, `schedule_events`).

Conflict resolution: if a subject already exists in the database, the scraper compares block counts and only replaces the schedule if the new scrape yields more valid blocks than the existing data.

### Free Room Algorithm (Time-Shifting)

The "Free Rooms" feature (`get_currently_free_rooms()` in `services/wsp_repo.py`) identifies classrooms that are not occupied at the current moment.

#### The Problem

At KBTU, class periods typically end at `XX:50` and the next period begins at `(XX+1):00`, creating a 10-minute break window. If a student queries free rooms at, for example, `10:55`, all rooms are technically "free" during this break — but many of them will be occupied again at `11:00`. Returning rooms that are free for only 5 minutes is unhelpful.

#### The Solution

The algorithm applies a **15-minute forward time-shift** when the current minute is `≥ 50`:

```python
if now.minute >= 50:
    target_time = now + timedelta(minutes=15)
else:
    target_time = now
```

| Current Time | `minute >= 50`? | Target Time | Effect |
|---|---|---|---|
| `10:30` | No | `10:30` | Returns rooms free right now |
| `10:55` | Yes | `11:10` | Returns rooms free during the next class period |
| `11:50` | Yes | `12:05` | Returns rooms free during the next class period |

The query then checks for rooms where no `ScheduleEvent` overlaps the target time on the current weekday:

```python
select(Room.number).where(
    ~Room.events.any(
        and_(
            ScheduleEvent.day_of_week == current_day,
            ScheduleEvent.start_time <= check_time,
            ScheduleEvent.end_time >= check_time
        )
    )
)
```

This ensures students receive rooms that will remain available for the upcoming class period, not just the current break interval.

### Output Formatting

The `format_free_rooms()` function in `utils/formatters.py` post-processes the raw room list:

1. **Blacklist filtering** — removes non-physical or external locations (e.g., "онлайн", "ИХН", "Jastar City").
2. **Floor grouping** — rooms are categorized by floor based on their numeric prefix (e.g., `332б` → floor 3), with explicit mappings for special rooms (e.g., `"Independence Hall"` → floor 2).
3. **HTML formatting** — output is grouped by floor with bold headers for Telegram's HTML parse mode.
